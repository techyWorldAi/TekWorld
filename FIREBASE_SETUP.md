# Firebase and Cloudinary setup

The web app reuses the existing Firebase project and Firestore database. CMS image uploads go directly from the browser to Cloudinary. The CMS does not initialize Firebase Storage or use Firebase Admin SDK credentials.

## Firebase Console setup

1. In Firebase Console, select project `tekworld-d57ca` and confirm that its existing named Cloud Firestore database has database ID `default`. Do not create another database or overwrite existing content.
2. Under **Authentication → Sign-in method**, enable **Email/Password** and create administrator users under **Authentication → Users**.
3. Copy each administrator's UID. Through Firebase Console or a trusted server/Admin SDK process, create `admins/{uid}` in the existing `default` database with the boolean field `enabled: true`. The site can read only the signed-in user's own admin record; users cannot grant themselves access.
4. Configure the Firebase web-app values in `.env.local` or the hosting provider's build environment. Review the target and deploy the checked-in Firestore rules:

   ```bash
   firebase deploy --only firestore:default --project tekworld-d57ca
   ```

5. Build and deploy the site after setting the environment variables. Direct `/work/{slug}` paths are supported by the GitHub Pages SPA fallback generated by the production build.

The browser uses `projects`, `services`, `companies`, `siteSettings/homepage`, `admins`, and `enquiries` in the existing database. Public users can read published projects/services/companies/pages and the homepage settings document. Only authorized administrators can write CMS content or read/manage enquiries. Visitors may create bounded contact enquiries. Admins and drafts are not public.

Firestore uses a persistent IndexedDB local cache (shared safely across open tabs). Public content is displayed from that cache immediately, then refreshed in the background when its five-minute freshness window expires; successful CMS edits invalidate freshness markers and trigger a refresh. This keeps repeat visits responsive while allowing refreshed content to appear without a full-page wait. Firestore data is structured text/metadata only—image bytes are delivered and cached by Cloudinary's CDN and the visitor's browser, not fetched from Firestore.

## Cloudinary setup

1. Create or select the Cloudinary account and copy its **Cloud name** from the account dashboard.
2. In **Settings → Upload → Upload presets**, create a dedicated preset for TekWorld. Set **Signing Mode** to **Unsigned**. Do not use an API secret or signed-upload secret in the web app.
3. Restrict the preset to image uploads, allow only the formats used by the site (JPEG, PNG, WebP, and AVIF), set a maximum file size no greater than the CMS limit of 10 MB, and set an appropriate destination folder. Restrict transformations and other preset options as tightly as the account allows.
4. Put the cloud name and exact unsigned preset name into the build environment:

   ```dotenv
   VITE_CLOUDINARY_CLOUD_NAME=
   VITE_CLOUDINARY_UPLOAD_PRESET=
   ```

   The Firebase client variables required alongside them are `VITE_FIREBASE_API_KEY`, `VITE_FIREBASE_AUTH_DOMAIN`, `VITE_FIREBASE_PROJECT_ID`, `VITE_FIREBASE_MESSAGING_SENDER_ID`, and `VITE_FIREBASE_APP_ID`. Copy the names from `.env.example`. `VITE_FIREBASE_STORAGE_BUCKET` is not required.
5. Rebuild after changing the configuration. In the admin project, service, or company editor, use the relevant image uploader. The browser sends the selected image to Cloudinary's HTTPS upload API. The returned `secure_url`, `public_id`, alt text, width, and height are stored in Firestore; image bytes are never stored in Firestore.

The project's **Gallery images** control accepts multiple files at once and also allows adding more in later uploads. Published project detail pages automatically cycle through the gallery, with previous/next buttons and image indicators. The carousel pauses while hovered or focused and does not autoplay when reduced motion is preferred.

Public Cloudinary images use responsive `srcset` variants (160, 320, 640, 960, and 1280 pixels) with automatic format/quality selection and width-limited delivery. The first featured project image and first company logos start loading immediately; lower-page imagery remains lazy-loaded. The hero background is preloaded and compressed for fast first paint. The browser selects an appropriate size for its viewport and may reuse its normal HTTP image cache on repeat views.

In **Pages & Homepage**, admins can reorder or hide the existing hero, services, featured work, companies, and contact sections, choose the site's accent color, edit hero text, and select featured projects. This preserves TekWorld's existing responsive component designs rather than exposing a freeform drag-and-drop canvas. Uploaded service images are shown on their public service cards; companies render in their own public section when published.

Unsigned upload configuration is public and is not an administrator authorization mechanism. Treat every uploaded asset as public. Restrict formats, file size, destination, and preset behavior in Cloudinary. Unsigned uploads do not provide per-admin upload authorization and may be abused if the preset is discovered; monitor Cloudinary usage and configure account limits/alerts. If strict per-user upload authorization, private media, or stronger abuse protection is required, implement a trusted server-side signed-upload endpoint and keep its API secret server-side. Cloudinary plan quotas, transformations, and features may change; confirm current account limits and costs in Cloudinary. No paid Cloudinary feature is assumed by this client flow.

The media library lists Cloudinary assets referenced by current Firestore content. Removing an image only detaches its reference. Asset deletion is deliberately unavailable in the browser because deleting Cloudinary media safely requires trusted credentials and a cross-reference check.

## Data compatibility and limitations

- The application explicitly connects to the existing Firestore database ID `default` (`projects/{projectId}/databases/default`). It does not create or migrate a Firestore database.
- Project and service document IDs are their slugs. Writes check slug collisions transactionally; changing a slug moves the document.
- Public project/service/company queries exclude drafts through `published`/`status` filters. No Firestore composite indexes are currently required.
- Firebase Storage rules remain in `storage.rules` but are not needed by the CMS. Do not deploy them as part of this setup.
- Legacy Supabase records are left untouched, but the browser-side Supabase loader has been removed. Export, review, and import any required legacy stories or company records into Firestore before retiring their old source. No automatic migration is performed.
- Existing external image URLs remain supported for compatibility. Newly uploaded files use Cloudinary.

## Local development

Use an ignored `.env.local` file with the names in `.env.example`, then run:

```bash
npm install
npm run dev
npm run build
```

Never commit `.env.local`, service-account JSON, Firebase Admin SDK credentials, or Cloudinary API secrets.
